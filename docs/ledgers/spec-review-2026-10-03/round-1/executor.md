## Findings

1. **The form focus fallback cannot meet the stated legibility bar.** The spec keeps the entire power band unchanged, with 19 base powers “one per row,” then adds the form band. `forms_focus` only filters forms. At 640×360, that fallback still leaves 19 power rows and does not address the combined graph’s vertical space. The spec gives no node spacing, canvas dimensions, or edge-routing rule that would make the bar verifiable. Define a fallback that actually reduces the graph, or change the legibility requirement. The claimed 24 forms plus slime root also means 25 form nodes before stubs.

2. **Form persistence can silently fail, and the malformed-data requirement exceeds what `Profile` provides.** `Profile.dict_section()` at [profile.gd](/Users/sean/sites/isekai-game/scripts/persistence/profile.gd:59) checks only that the section’s top-level value is a dictionary. A `{species: {form_id: "reached"}}` section can still contain malformed nested values. Also, `Profile.save()` returns `false` on write, parse, or rename failure ([lines 70–89](/Users/sean/sites/isekai-game/scripts/persistence/profile.gd:70)); the spec does not say how `FormLog` handles or reports that failure. Specify nested validation and save-failure behavior, or “malformed section is dropped and warns” is not guaranteed.

3. **The HUD’s persistent ready indicator needs explicit refresh triggers.** The spec defines it by current readiness *and affordability*, but `evolution_ready` fires when conditions become ready ([skill_rules_engine.gd](/Users/sean/sites/isekai-game/scripts/skills/skill_rules_engine.gd:244)). A ready evolution can initially be unaffordable, then become affordable when more essence is absorbed. Conversely, paying for one evolution can make another unaffordable. State which events refresh the indicator; relying on the ready signal alone leaves it stale.

4. **The new `FormDef.powers` field is not fully specified at its source of truth.** The current generator assigns stage-2 form essences through `essences_of()` in [build_forms.gd](/Users/sean/sites/isekai-game/tools/build_forms.gd:97) and defines those lists at [lines 106–118](/Users/sean/sites/isekai-game/tools/build_forms.gd:106). The spec says to replace `essences` with `powers` and gives a separate lineage-power table, but does not explicitly require replacing the generator’s mapping and regenerating the `.tres` files. Without that step, forms keep affinity data and the new `FormOffers`/tree logic has no authoritative lineage-power lists.

5. **The “every creature carries elements” success criterion contradicts the derived table.** The table explicitly leaves the Cave Serpent with no elements. Either the criterion needs an exception or the table needs a deliberate assignment; otherwise the implementation cannot satisfy both.

6. **The new spider-family unlock is under-validated.** `Player._complete_predation()` currently emits `PREDATED` with only `source` and `kind` ([player.gd](/Users/sean/sites/isekai-game/scripts/player/player.gd:807)); adding `family` there is feasible. But the current validator checks event names, source tags, and essence tags—not arbitrary tag values ([def_validator.gd](/Users/sean/sites/isekai-game/scripts/skills/def_validator.gd:116)). Add a defined validation rule for family tags, or a typo in the family recipe will pass validation and make Sticky Thread impossible to unlock. Also clarify that “third spider” means three qualifying predations across both Black Spider and Taratect, since both receive the family tag.

7. **The all-node directional-navigation test does not establish a usable navigation graph.** `neighbor(id, dir)` is defined as the nearest node in a direction, while the test requires every node to be reachable from the root. The spec does not define behavior for ties, diagonal placement, or directions with no candidate; with rows ordered by name and edges crossing between bands, geometric nearest-neighbor moves can strand nodes even when the rendered graph is connected. Specify deterministic tie-breaking and test reachability using the actual directional-neighbor relation.

8. **The claimed test-list cleanup misses visible EP and affinity dependencies.** `Progression.ep` is incremented and preserved by `start_at()`/`evolve_stage()` in [progression.gd](/Users/sean/sites/isekai-game/scripts/actors/progression.gd:46), and the old affinity flow remains wired through `Player.form_offers()` ([player.gd](/Users/sean/sites/isekai-game/scripts/player/player.gd:561)) and `RebirthKit.apply()` ([rebirth_kit.gd](/Users/sean/sites/isekai-game/scripts/world/rebirth_kit.gd:76)). The spec’s changed-test list names selected files but omits `tests/test_progression_stages.gd`, `tests/test_rebirth_flow.gd`, and `tests/test_skill_caps.gd`, which directly exercise EP or essence totals. The stated migration is therefore incomplete unless those tests are accounted for.

I did not run the test suite: this is a read-only plan review, and the requested suite command, `tools/run_tests.sh`, creates and removes files under `.tmp/`.
